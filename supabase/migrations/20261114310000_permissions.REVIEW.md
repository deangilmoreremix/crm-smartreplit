# Review notes: 20261114310000_permissions.sql (and 20261114300000_data_model.sql)

## Model
There is no `workspaces` table. The workspace is the **owner's user id**. `team_members(owner_id, member_id, role_id, status)`
links other users into an owner's workspace; `roles` belong to an owner. `object_type` is the standard object name
(`contacts`, `deals`, `tasks`, `companies`) or, for custom objects, `object_metadata.id::text`.

## Key semantics: policies are OR'd
Postgres combines multiple permissive policies for the same command with OR. Every policy added here is **additional
and permissive**; the existing owner policies are not dropped or rewritten. So these policies can only ADD access for
team members; they cannot restrict the owner or anyone already granted access by an existing policy. If a legacy table
has a broad policy (e.g. `USING (true)`), role permissions do not narrow it. Policies are added only as SELECT and UPDATE
(no INSERT/DELETE for members; members create/delete only through the API).

## Tables (all RLS enabled)
- `roles`: owner ALL; members SELECT their own role row (`roles_member_select`).
- `role_object_permissions`, `role_field_permissions`: owner ALL via parent role ownership. Members cannot read them directly (functions do).
- `team_members`: owner ALL; member SELECT own row (`team_members_self_select`, read-only so a member cannot self-promote).
- Data model tables (`object_metadata`, `field_metadata`, `records`, `record_relations`, `custom_field_values`): owner ALL.

## Functions (all `SET search_path = public`, EXECUTE revoked from PUBLIC/anon, granted to authenticated)
- `visible_owner_ids()` SECURITY DEFINER STABLE: caller + owners whose active team the caller belongs to.
- `member_role_id(owner)` SECURITY DEFINER STABLE: caller's role id in that team.
- `has_object_perm(owner, object_type, action)` SECURITY DEFINER STABLE: owner => true; active member => role grant for read/create/update/delete; else false.
- `has_field_perm(owner, object_type, field, 'read'|'write')` SECURITY DEFINER STABLE: default allow when no row; owner always.
- `mask_record_data(owner, object_type, data)` SECURITY DEFINER STABLE: strips non-readable keys. Deviation from the brief: takes `owner` as first arg because the caller's role cannot be resolved without it.
- `enforce_field_write_perms()` trigger (`trg_records_a_field_perms`, BEFORE UPDATE on `records`): for non-owner authenticated users rejects changes to keys without write permission and any change of `user_id`/`object_id`. Skipped when `auth.uid()` is NULL (service role).
- `records_maintain()` / `custom_field_values_touch()` triggers (data model migration): maintain `updated_at` and `search_text` (not SECURITY DEFINER; pure row logic).

SECURITY DEFINER rationale: the permission tables have owner-only RLS; the functions must read them on behalf of a member, and
calling them inside a policy on another table would otherwise cause policy recursion. They always key on `auth.uid()` (never a
caller-supplied identity), have a pinned search_path, and only return booleans/ids/masked data.

## Policies added
`records_member_select|update`, `custom_field_values_member_select|update`, `object_metadata_member_select`,
`field_metadata_member_select`, and (DO block, only if table exists and has a uuid `profile_id`/`user_id`) `team_member_select`
and `team_member_update` on contacts/deals/tasks/companies. Each requires `owner <> auth.uid()` AND `has_object_perm(...)`.

## Known limits
- **Field-level permissions are partial.** Enforced for `records.data` (write: trigger; read: only if the caller uses
  `mask_record_data` or the API, which masks). RLS cannot hide JSON keys, so direct PostgREST SELECT of a `records` row a member may read
  returns all keys. For legacy tables (typed columns) no column masking is implemented; use the API or views. Treat field read
  restrictions as UI/API-level, not a hard DB guarantee, unless clients are forced through the API.
- Service-role API calls bypass RLS and triggers; the API (`server/routes/dataModel.ts`) re-implements the checks.
- `has_object_perm` runs per row (it depends on row columns, so it cannot be an init-plan); indexes on owner columns matter.
- Legacy-table policies are inert if RLS is not enabled on that table, and do nothing for tables lacking a uuid owner column.
- Invited members have `member_id` NULL until they sign up; the API links them on first lookup by email. Until `status='active'` they see nothing.
- Custom objects use the object's uuid as `object_type`; deleting an object leaves orphan permission rows (harmless).

## Update 2026-11: API-only for custom objects
**Supersedes the "Field-level permissions are partial" limit above for custom objects.** Migration
`20261116100000_records_api_only.sql` revokes ALL privileges on `records`, `custom_field_values` and `record_relations` from
`anon`, `authenticated` and `PUBLIC` (and EXECUTE/SELECT on `records_masked_rows` / `records_masked`); only `service_role` keeps
access. Custom-object data is reachable only through `/api/data-model/*` (service role, object + field permissions enforced and
masked in `server/routes/dataModel.ts`). The member policies listed above stay in place with RLS enabled, but are unreachable
for browser roles (privileges are checked before RLS). Field read restrictions on custom objects are therefore a hard guarantee,
as long as nobody re-grants these tables to browser roles; `supabase/tests/rls.sql` (sections 2d-2f) fails if that happens.
Still true: legacy `contacts`/`deals`/`tasks` are not column-masked in the database, and the owner always sees everything.
Details and trade-offs: `20261116100000_records_api_only.REVIEW.md`.
