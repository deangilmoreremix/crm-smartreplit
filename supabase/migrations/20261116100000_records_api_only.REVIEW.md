# Review: custom-object data is API-only (20261116100000_records_api_only.sql)

## Guarantee
Browser roles (`anon`, `authenticated`, i.e. any holder of a Supabase JWT calling PostgREST or Realtime) have **no privileges** on
`public.records`, `public.custom_field_values`, `public.record_relations`, and no EXECUTE on `records_masked_rows` / SELECT on
`records_masked`. The only path to custom-object data is the Netlify API (`server/routes/dataModel.ts`, service role), which checks
object permissions and masks fields (`maskData`) in code. So a role that cannot read field X can never obtain X for a custom object,
regardless of RLS or JSON-key limitations of the database.

## What changed
- `REVOKE ALL ... FROM PUBLIC, anon, authenticated` on the three tables; `GRANT ALL ... TO service_role`.
- `REVOKE ALL` on `records_masked` and `records_masked_rows(uuid)` from `PUBLIC, anon, authenticated`; `service_role` only.
- RLS stays ENABLED on the three tables and the existing owner/member policies are **kept** (not dropped). They are now unreachable
  (privilege checks run before RLS), i.e. deny-by-default for non-service roles, and act as defence in depth if a grant is ever re-added.
  Dropping them would remove that net and gain nothing.
- The three tables are removed from the `supabase_realtime` publication if present.
- `object_metadata` / `field_metadata` policies are unchanged: the browser may still read metadata (labels, field definitions).
- Idempotent; each statement is guarded (`to_regclass` / `to_regprocedure` / role existence).
- API change in `dataModel.ts`: for callers with hidden fields on the object, `q` no longer uses `search_text` (derived from ALL fields,
  would match hidden values). The server scans keyset pages (500 rows, at most 2000 scanned) and matches case-insensitively on the
  MASKED data only; `nextCursor` lets the client continue past the bound. Filters on hidden fields are rejected (400, "unknown field").
  Owners and unrestricted callers keep the fast `search_text` path. `search_text` and unmasked `data` are stripped from every response
  (list, create, update). No SQL is built from user input.

## Trade-offs
- Realtime subscriptions on `records` are no longer available to browsers (they would also bypass masking). Use polling / refetch via the API.
- Restricted-role search is O(scan), bounded at 2000 rows per request: matches beyond that need follow-up pages via `nextCursor`.
- Any new direct supabase-js read of these tables breaks by design; client code only calls `/api/data-model/*` (verified by grep).
- `has_read_restrictions`, `visible_owner_ids`, `mask_record_data` stay callable by `authenticated`; they only reveal the caller's own permissions.

## Remaining limits
- Legacy `contacts` / `deals` / `tasks` / `companies` are typed-column tables: no field masking at database level (API/UI level only).
- The owner always sees everything (by design). Service-role code paths bypass RLS; the API is the enforcement point and must keep checking.
- Standard-object custom values (`custom_field_values`) are also API-only now; `/api/data-model/custom-values` already uses the service role.
- Future migrations that run `GRANT ... ON ALL TABLES` or rely on default privileges can re-open these tables; `supabase/tests/rls.sql`
  (2d-2f) fails when that happens, so keep running it after every migration.
