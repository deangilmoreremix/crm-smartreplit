# Review: 20261114410000_webhooks_api.sql

Scope: outbound webhooks (`webhooks`, `webhook_deliveries`), public API keys (`api_keys`, `api_key_usage`),
DB triggers on contacts/deals/tasks/companies. Companion: `20261114400000_workflow_automation.sql`.

## 1. RLS
| Table | RLS | Authenticated policy | Notes |
|---|---|---|---|
| `webhooks` | on | `FOR ALL` where `auth.uid() = user_id` | **Column grants**: `SELECT` revoked from `authenticated`/`anon`, re-granted on every column except `secret`. A browser using the anon key can never read a signing secret. API routes use the service role and always filter `user_id`. |
| `webhook_deliveries` | on | `SELECT` only, via parent webhook owner | Written only by the trigger function (SECURITY DEFINER) and the worker (service role). |
| `api_keys` | on | `FOR ALL` where `auth.uid() = user_id` | `SELECT` revoked, re-granted on every column except `key_hash`. |
| `api_key_usage` | on | none (service role only) | Counter written via `bump_api_key_usage` (EXECUTE only for `service_role`). |

Residual: an owner can INSERT an `api_keys` row directly through PostgREST with a `key_hash` of their choosing
and any scopes. That only yields access to their own data (every v1 query is filtered by the key owner), so it is
not an escalation. If you want it closed, drop the INSERT/UPDATE policy and keep writes server-side only.
`companies` is the tenant table: an `owner_user_id` owner can already manage it; the API never creates/deletes it.

## 2. Trigger payload exposure
- `enqueue_webhook_deliveries()` stores `to_jsonb(NEW)` (or `OLD` on delete): **every column** of the row, including
  PII (emails, phones, notes), `tenant_id`, `profile_id`. Recipients are only the row owner's own active webhooks
  (`webhooks.user_id = owner column`), so the data goes where the owner configured it, but it also sits in
  `webhook_deliveries.payload` (readable by the owner through RLS) until deleted. Recommended follow-ups: a retention job
  (e.g. delete deliveries older than 30 days) and, if some columns must never leave, switch the function to
  `to_jsonb(NEW) - 'tenant_id' - ...`.
- The function is `SECURITY DEFINER` with `search_path = public`, EXECUTE revoked from PUBLIC/anon/authenticated, and wraps its
  body in `EXCEPTION WHEN OTHERS` so a webhook problem can never fail the user's write.
- Triggers are created only where `to_regclass('public.<table>')` exists; owner column is per table
  (`profile_id`; `owner_user_id` for `companies`). Rows with no owner are skipped.
- Same pattern in `workflow_event_queue` (migration 20261114400000): service-role only, no policies.
- Outbound requests: https only, hostname resolved and rejected if any address is private/link-local/CGNAT/metadata,
  redirects disabled, 10s timeout. Remaining gap: DNS rebinding between our lookup and `fetch`'s own lookup (TOCTOU);
  mitigated by the short window, no redirects, and response bodies truncated to 1 KB, but not eliminated.
- Signature: `X-SmartCRM-Signature: sha256=HMAC_SHA256(secret, "<unix ts>.<raw body>")` plus `X-SmartCRM-Timestamp`;
  receivers should reject timestamps older than ~5 minutes to stop replays.
- `webhooks.secret` is stored in plaintext because the worker must compute HMACs. It is shown once at creation/rotation and
  is not selectable by browser roles (see 1). Encrypt-at-rest with a server key would be a further hardening step.

## 3. Key hashing
- Format `sk_live_` + 43 base64url chars (256 bits of randomness). Only `HMAC-SHA256(API_KEY_PEPPER, key)` is stored; the key is returned
  once by `POST /api/public-api-keys`. The pepper is an env var and is never in the database: a DB leak alone does not allow
  offline guessing or use of keys. Rotating the pepper invalidates all keys.
- Lookup uses the non-secret `prefix` (first 16 chars) then `timingSafeEqual` on the hashes. Responses for unknown/revoked/mismatched keys are identical.
- High-entropy keys make a fast hash appropriate (no password-style stretching needed).
- Revocation is soft (`revoked_at`) and checked on every request. `last_used_at` is updated at most once per minute.
- Rate limit: 120 requests/min/key via atomic `INSERT .. ON CONFLICT DO UPDATE` counter in `api_key_usage`; falls back to an
  in-memory counter if the RPC fails. Old counter rows are pruned hourly by the scheduler.
- Global middleware note: the existing `jwtSession` middleware tries `auth.getUser(token)` for any `Bearer` token, so each API-key
  request costs one failed Supabase auth call (no security impact, only latency). Skipping `sk_live_` tokens there would remove it.
